# MVP публичного лидерборда

## Выбранный сценарий

Участники загружают не исполняемый код, а готовый файл результата алгоритма.
Платформа проверяет файл, пересчитывает стоимость и длину по геометрии, применяет
правила допуска и обновляет публичный лидерборд.

Этот вариант не требует sandbox для запуска чужого кода и подходит для первого
публичного прототипа.

## Основной пользовательский поток

1. Участник регистрирует команду.
2. Участник выбирает датасет.
3. Участник загружает файл результата.
4. Система сохраняет сабмит в статусе `queued`.
5. Верификатор проверяет формат и критичные правила.
6. Если сабмит допущен, система пересчитывает `C` и `L`.
7. Система выбирает лучший вариант команды для датасета.
8. Система пересчитывает `C_min`, `L_min`, `Score_d` и `Total`.
9. Публичный лидерборд обновляется.

## Правила допуска

Сабмит получает `Score_d = 0`, если:

- файл результата не соответствует формату;
- верификатор нашел критичные ошибки;
- время расчета превышает `T_max`, если время предоставляется и проверяется организатором;
- файл невозможно разобрать или пересчитать.

Критичные ошибки:

- пересечение новых трасс без узла сети;
- вход трассы в здание;
- нарушение минимальных расстояний;
- больше четырех участков в одной камере;
- диаметр участка ниже требуемого расходом.

Некритичные замечания не дисквалифицируют сабмит, но сохраняются в отчете.

## Скоринг

Для каждого датасета:

```text
Score_d(i) = 0.7 * C_min(d) / C_i(d) + 0.3 * L_min(d) / L_i(d)
```

Где:

- `C_i(d)` - пересчитанная стоимость решения команды на датасете;
- `L_i(d)` - пересчитанная длина новой и реконструируемой сети;
- `C_min(d)` - минимальная стоимость среди допущенных сабмитов;
- `L_min(d)` - минимальная длина среди допущенных сабмитов.

Итог:

```text
Total(i) = average(Score_d(i))
```

Пропущенный датасет считается как `Score_d = 0`.

Если команда загрузила несколько вариантов на один датасет, в лидерборд идет лучший
вариант по показателю:

```text
S = 0.7 * C / 25_000_000 + 0.3 * L / 100
```

## Тай-брейки

Команды считаются равными, если:

```text
abs(Total_a - Total_b) <= 0.005
```

Равенство разрешается последовательно:

1. меньше суммарное время расчета;
2. меньше суммарная стоимость;
3. меньше суммарная длина.

## Публичный интерфейс

Минимальная таблица:

- место;
- команда;
- итоговый score;
- суммарное время;
- суммарная стоимость;
- суммарная длина;
- статус по каждому датасету;
- score по каждому датасету.

Страница команды:

- список сабмитов;
- выбранный лучший сабмит по каждому датасету;
- отчет верификатора;
- причины отказа, если сабмит не допущен.

## Админский интерфейс

- создать датасет;
- скрыть или опубликовать датасет;
- включить или выключить датасет в рейтинге;
- настроить `T_max`;
- посмотреть все сабмиты;
- скачать исходный файл результата;
- скачать отчет верификатора;
- запустить повторную проверку;
- вручную снять сабмит с рейтинга с указанием причины.

## Что понадобится после получения датасета

1. Точный формат входного датасета.
2. Точный формат файла результата участника.
3. Правила пересчета стоимости `C`.
4. Правила пересчета длины `L`.
5. Список геометрических проверок и допустимые погрешности.
6. Формат отчета верификатора.
7. Нужно ли проверять время расчета в варианте A или оно будет только справочным.

## Наблюдения по примеру датасета

Примерный архив: `heat_network_datasets_2026-09-21.zip`.

Опорные файлы:

- `data/benchmark_specs/rule_catalog.json` - числовой каталог труб, камер, штрафов,
  весов и коэффициентов;
- `data/benchmark_specs/benchmark_cases.json` - каталог тест-кейсов для будущего
  верификатора;
- `data/benchmark_fixtures/new_tz_smoke/input.geojson` - маленький входной пример;
- `data/benchmark_fixtures/new_tz_smoke/valid_result.geojson` - маленький валидный
  результат;
- `data/rl_large_smoke/scene_manifest.json` - манифест сцен с `scene_id`,
  `split`, путем к входному GeoJSON и hash;
- `data/rl_large*/scenes/**/*.geojson` - основные сцены для загрузки в систему.

Входной датасет представлен как GeoJSON `FeatureCollection`. Тип объекта лежит в
`feature.properties.object_type`.

Обнаруженные входные `object_type`:

- `source`;
- `heat_network`;
- `heat_chamber`;
- `oks_connection_point`;
- `restriction`.

Для `restriction` используется `restriction_type`, например:

- `road`;
- `water`;
- `oks`;
- `railway`;
- другие ограничения из OSM/подготовленного набора.

Результат участника тоже представлен как GeoJSON `FeatureCollection`.
Минимально ожидаемые выходные `object_type`:

- `heat_network`;
- `heat_chamber`;
- `variant_summary`.

Примерные поля `heat_network`:

- `id`;
- `object_type`;
- `variant_id`;
- `start_node_id`;
- `end_node_id`;
- `flow_tph`;
- `diameter`;
- `length`;
- `laying_method`;
- `cost`.

Примерные поля `heat_chamber`:

- `id`;
- `object_type`;
- `variant_id`;
- `diameter`;
- `cost`.

Примерные поля `variant_summary`:

- `variant_id`;
- `rank`;
- `construction_cost`;
- `chamber_construction_cost`;
- `existing_chamber_tie_in_count`;
- `existing_chamber_tie_in_cost`;
- `unconnected_penalty`;
- `calculated_cost`;
- `new_network_length`;
- `length`;
- `score`;
- `unconnected_oks_ids`;
- `diagnostics`.

Для публичной борды нельзя доверять `variant_summary` напрямую. Его нужно хранить
как заявленную сводку участника, а рядом сохранять пересчитанные организатором
`calculated_cost`, `new_network_length`, `length`, `score` и расхождения.

## Импорт датасета из архива

Для MVP достаточно импортировать не весь архив, а выбранный manifest:

1. Прочитать `scene_manifest.json`.
2. Для каждой записи создать `Dataset`.
3. Сохранить:
   - `scene_id`;
   - `parent_scene_id`;
   - `split`;
   - `city`;
   - `research_bucket`;
   - `input`;
   - `input_hash`;
   - `feature_count`;
   - `restriction_count`;
   - `oks_count`.
4. Скопировать соответствующий `input.geojson` или сохранить ссылку на файл в
   распакованном хранилище.
5. Использовать `split = test` для публичного/закрытого рейтинга по решению
   организатора, а `train` и smoke-сцены - для самопроверки участников.

## Минимальный верификатор для первого прототипа

До полноценной геометрической проверки можно сделать первый слой, который:

- проверяет, что результат является GeoJSON `FeatureCollection`;
- проверяет уникальность `properties.id`;
- проверяет наличие ровно одной `variant_summary` на `variant_id`;
- проверяет, что числа конечные: без `NaN`, `Infinity`, строк вместо чисел;
- проверяет наличие обязательных полей у `heat_network`, `heat_chamber`,
  `variant_summary`;
- проверяет, что `diameter` есть в `pipe_catalog`;
- проверяет, что `flow_tph` не превышает `capacity_tph` для выбранного диаметра;
- пересчитывает длины LineString-участков;
- пересчитывает стоимость новых участков по `new_rate_rub_per_m`;
- пересчитывает стоимость камер по `chamber_costs`;
- пересчитывает штраф за `unconnected_oks_ids`;
- сравнивает пересчитанные значения с заявленными в `variant_summary`.

Полный верификатор потом добавит геометрию:

- пересечения трасс без узла;
- вход трассы в здание;
- минимальные расстояния;
- степень камеры больше 4;
- реконструкции существующей сети;
- спецкоэффициенты пересечений и зон.
